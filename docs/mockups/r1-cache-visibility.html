Where a match's candidates came from, and how old they are

Every FoodData Central answer is kept forever under the exact words FDC was asked; the review sheet's candidate list and the search box both read it. Nothing said so, and nothing offered a way past it. This adds one quiet line with the age and one action — Search live — that spends a single FDC request and replaces the stored answer for everyone (the next compute of any line with that ingredient sees it too).

1 · The fix panel — candidates from the cache, with their age

Under the candidate list, where today's panel already says "No other cached matches for this line" when there are none. The line names what FDC was actually asked — after the matcher's rewrites, so the admin sees spices pepper black for a pepper line and understands the results — and when.

2 · A hand search, and what it says about its own answer

The same line under the results, in the same words. A cached answer offers Search live; a live one says so and offers nothing more. Every state is one line, never a banner.

Cached — the common case

Live — just fetched (or refreshed): the age is “just now”, and there is nothing to refresh
Results for “pepper spice”

Never asked — a line whose candidates were never fetched (water, seasoning to taste, an empty item)

No line at all. The panel's existing “No other cached matches for this line” stands, and the hand search is the way to ask.

3 · What the app needs from the server (shipped)
Per linecandidates_cached_at on every matches line: when FDC was last asked for that line's candidates, null if never.
Per searchGET /api/v1/nutrition/search?q=… now answers query (the words FDC was asked), cached, cached_at.
Live&fresh=true bypasses the cache, spends one FDC request, and replaces the stored row — so a later compute uses the new answer too. Admin only, like every search.
