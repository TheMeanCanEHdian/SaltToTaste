Nutrition matches, grouped by ingredient

202 flagged lines are only 131 ingredients. A wrong food is an ingredient-level problem — the decision is stored against item_key and reaches the whole library — so in the food buckets the queue's unit of work becomes the ingredient. Nothing new is invented: the same filter chips, the same two-pane card, the same fix pane opened on one real line of the group, the same apply-to-all strip, the same advance-after-fix. What the user is being asked to approve is the group row, an Ingredients / Lines toggle with a per-bucket default, and four exact server additions.

Data. Every recipe, line, food, count and confidence on this page was queried out of the recomputed diagnostic copy — .claude/diag/2026-09-08/work.db: the 69-recipe sweep recomputed cache-only with the matcher that ships today, 0 provider calls. Measured there: 202 flagged lines out of 878, 131 groups, 102 of them a single line, and — checked, not assumed — 0 groups whose flagged lines sit in two buckets and 0 on two different foods. Buckets: no match 4, no grams 80 (46 ingredients), low confidence 118 (81 ingredients), skipped 0; the other 676 lines are counted. The diag.db sitting beside it is the pre-fix sweep (223 / 144 / 112), computed before the ranker fixes shipped — it is not what ships, and nothing on this page quotes it.

Today others is COUNT(DISTINCT recipe_id) of undecided rows with this item key that are not already on this food (salt_database.dart, … AND (? IS NULL OR fdc_id IS NULL OR fdc_id != ?)). 4 · The toggle, and why each bucket opens differently

One two-cell segment at the right end of the existing header line, next to the count it changes, in the theme's neutral grey — it switches a view, it is not a primary action, so it is never maroon. It sets the unit of the list and nothing else: chips, card, pane, strip and sort are identical in both. The default is one expression — grouped = bucket != 'no_grams' && bucket != 'skipped' — and a flip is remembered for that bucket for the session (one map on the cubit), so changing chips does not undo it.

Need attentionIngredients. Mixed work, and the food problems dominate: the food buckets hold 122 of the 202 lines.
No matchIngredients. A missing food is an ingredient's problem by definition. All four here are single-line groups, so the rows are today's rows.
Low confidenceIngredients. The leverage case: 81 ingredients over 118 lines.
No gramsLines. The food is already right (every multi-line group here sits at 61–100%, and most of them are a herb or a spice); each line's amount is its own question and {grams} never travels. Ingredients stays selectable as a map — see below.
SkippedLines, and the segment is hidden. A skip is per line and never travels, so an ingredient row there would promise a reach the API refuses. Hidden beats disabled: no dead control to click.

6 · “Worst first” for groups, and which line is the example
SortMIN(confidence) ASC, then lines DESC, recipes DESC, item_key for a stable page boundary. A no match row stores confidence 0.0, not null, so no-food groups do not lead as a block — they tie with the 0% check groups and interleave with them: in Need attention grouped the first eleven rows are all single-line groups at 0.0–0.003, four no match and seven check, and the first multi-line group (herbe de provence) is row 12. A group is as bad as its worst line. Reach is the tie-break, never the key: sorting by reach would bury herbes de Provence → Dulce de Leche (3%, 2 lines) under cilantro leaf (8 lines at 92%).
Example lineThe group's lowest-confidence line; among ties one that has grams (so Confirm as-is is reachable when the food is fine); then recipe title, then position. Deterministic, so a reload never shuffles the work. Worked through: jalapeno chile → Cheesy Nachos line 2; lemon wedge → Chicken Schnitzel line 8 (no member has grams, so the title decides); makrut lime leaf → Guay Tiew Tom Yum Goong line 3 (both members are 264 g, so the title decides again); instant or rapid-rise yeast → Best Whole-Wheat Sandwich Bread line 2 (all six lines are 0.37 with grams — title first, then position 2 ahead of position 8 in the same recipe).
Header, groupedShowing <all flagged|bucket> · N ingredients, M lines · worst first.

7 · What the server and the app must add
PieceChange
Grouped modeGET /api/v1/admin/nutrition_review?group=item&bucket=&page=&limit= — a mode on the existing endpoint, same envelope. Without the parameter the response is exactly today's. No new endpoint.
Group item shapeToday's item, flattened, plus five fields. Each entry keeps recipe / position / raw / bucket / match — the example line, at top level — and adds item_key, lines, recipes, decided, grams: {min, max, missing}. This matters: NutritionReviewLine.fromJson reads those five keys at top level and key is slug#position, so the model, select(), _FixPane, FixPanel and queueShouldAdvance parse and behave unchanged. Nesting the example under example: {…} would break the parse for no gain.
Grouping keyThe existing ingredient_matches.item_key (indexed) — the same key ingredient_decisions is keyed by, so a group is precisely “what one decision fixes”. GROUP BY item_key over the same _reviewBucketCase derived table, inside the bucket filter. Rows with a null item_key stay ungrouped single rows.
Group bucket & confidenceWorst member wins (no_match > check > no_grams > skipped); confidence is MIN(confidence). Both free in the same aggregate.
Countstotal and buckets[].count stay line counts — the chips and the tab badge are untouched. Add groups at the top level and groups on each buckets[] entry, so the header can say “81 ingredients, 118 lines” and a chip can never disagree with it without a second request.
Amount aggregateMIN(grams), MAX(grams), COUNT(*) FILTER (WHERE grams IS NULL) — the row's amount slot. A range and a missing-count only; no plausibility judgment, because no API field can supply one.
decided flagtrue when ingredient_decisions holds the item key — one LEFT JOIN. Without it a group whose offer was declined looks untouched and gets decided twice.
others must be food-agnosticThe one change the grouped queue cannot ship without. Drop the same-food filter from otherRecipesUndecidedCount (… AND (? IS NULL OR fdc_id IS NULL OR fdc_id != ?)) so it means “undecided lines of this item key other than this one”, and report both units: keep others as the recipe count (the shipped field the strip already reads) and add others_lines — additive, so nothing that consumes others breaks. Same-recipe siblings already count (the SQL excludes only the one (recipe_id, position)), so saffron thread's 2-lines-in-1-recipe needs nothing extra.
apply_to_all reachThe same filter dropped in undecidedMatchesForItemKey, so the apply lands on undecided same-item lines that already carry this food — which is what makes them leave the check bucket. Its receipt applied:{recipes,lines,failed} is already the right shape.
Strip wordingOne conditional sentence in ApplyToAllStrip: “N other lines of <item>, in M recipes, are still waiting on this decision” when the decision kept the current food, today's “use <item> with a different match” when it changed. Same component, same buttons, same receipt.
Row labelThe raw item_key. There is no cheap display label: ingredient_matches stores no item text, ingredient_decisions.item exists only for ingredients already decided (which never appear in the queue), and the strip's label is computed app-side by itemLabel(row.item) from the parsed recipe document. A prettier label means a migration and a backfill — open question 2.
App stateNutritionReviewCubit: one grouped flag with a per-bucket map (grouped = bucket != 'no_grams' && bucket != 'skipped', session-remembered), forwarded as group=item; hasMore compares items.length against the group count in grouped view (it compares against a line count today, which would over-report); the header sentence; and the five optional fields on NutritionReviewLine. select(), loadMore(), completeFix() unchanged.
Deliberately not builtNo inline member list (the Lines toggle is the member view — decision 2), so no members[], no cap, no expansion state, no change to what “advance” means. No mixed-food or mixed-bucket UI (measured 0 of 131). No group-scoped Skip (open question 3). No new panel, no new endpoint, no new write.
8 · Open questions
  1. GO / NO-GO on the others widening. Nothing else here is contentious, and nothing else here works without it: a Confirm as-is on the commonest group shape (a food that is already right at 0.46–0.50) offers nothing and clears nothing today. The catch is that the same strip lives in the per-recipe match sheet, so offers would start appearing there on confirms that are silent now. Welcome — one confirm, whole library — or should the sheet keep the narrower count?
  2. Row label: raw item_key, or a display label? This page ships the key (“herbe de provence”, “nicoise olive”, “parsley leaf”) because it is honest, free, and the exact string the decision is keyed on. A label with accents and plurals restored needs an item column on ingredient_matches plus a backfill, or per-recipe document parsing inside the queue query.
  3. Group-scoped Skip? Six lemon-wedge and six lime-wedge garnish lines will never be weighable, and {skipped:true} is per line by design — twelve skips. A loop behind one button is trivial; whether the library should let one click do it is a decision about the data, not the UI.
  4. Members inline, later? This pass says no: the Lines toggle is the member view, which costs nothing and keeps “advance to the next row” meaning what it means today. If “let me check a second line before I decide for six recipes” turns out to be a habit rather than a hypothesis, an inline member list is a separate, additive change.
  5. Toggle memory: per bucket for the session (proposed — so the segment appears to move on its own when you change chips) or one setting for the whole tab?
  6. Do the chips ever count ingredients? Proposed: never — always lines, in both views, so the tab badge “Nutrition matches · 202” keeps its meaning and filteredTotal/hasMore keep working. The ingredient count lives in the header sentence only.
